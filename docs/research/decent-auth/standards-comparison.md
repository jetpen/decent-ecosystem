# Decentralized identity and authorization options for HTTP Bearer

**Research date:** 2026-10-05
**Context:** Wayfinder research ticket [#31](https://github.com/jetpen/decent-ecosystem/issues/31), under [shared ecosystem authentication/authorization map #29](https://github.com/jetpen/decent-ecosystem/issues/29). This comparison uses the scope and trust boundaries resolved in [#36](https://github.com/jetpen/decent-ecosystem/issues/36); it is research, not a scheme recommendation or architecture decision.

## Scope and current ecosystem baseline

The ecosystem's accepted MVP authentication is an application-level, fresh, short-lived, single-use wallet challenge signed with Ed25519. The user chooses the exact-match `decent-identity` Identity Record; the verifier resolves its current Registry-backed key and consumes the transaction once. Identity/Registry resolution alone is not authentication. The proof is not a reusable bearer token. WordPress owns its site session. Consent to disclose, storage access, and individual operations is separate from login; `decent-simple-storage` enforces its own capabilities and operator-approved onboarding/quota. Registry and Identity remain capability-neutral. See the [#11 resolution](https://github.com/jetpen/decent-ecosystem/issues/11), [Identity boundary](../../components/decent-identity.md), [WordPress boundary](../../components/decent-wordpress-auth.md), [Storage boundary](../../components/decent-simple-storage.md), and [MVP scope](../../vision/mvp-scope-and-non-goals.md).

The target `Authorization: Bearer <credential>` describes an HTTP presentation scheme, not a token encoding or issuer. RFC 6750 explicitly allows Bearer as a general HTTP authorization method for tokens “from any source”; the defining property is that possession suffices, without key proof. TLS is required. Thus a Bearer interface does **not** entail OAuth, JWT, or reusable wallet proof. [RFC 6750 §§1–2](https://www.rfc-editor.org/rfc/rfc6750.html)

## Detailed findings and exact boundaries

### Separate the proof, the credential, and each decision

Three objects are easy to conflate: (1) the user's single-use Ed25519 challenge response proving control for a login transaction; (2) a session/access credential issued after proof; and (3) the authorization decision for a particular storage object/action/purpose. The resolved ecosystem model keeps these distinct. Neither OIDC identity claims nor a successful OAuth login should silently confer permission to read/write a Storage Object. Operator enrollment/quota is another independent gate. [#11](https://github.com/jetpen/decent-ecosystem/issues/11), [#36](https://github.com/jetpen/decent-ecosystem/issues/36), [Storage boundary](../../components/decent-simple-storage.md)

### Bearer is a carrier contract, with a theft trade-off

RFC 6750 makes `Authorization: Bearer` the standard presentation and explicitly says any holder can use the token. It specifies neither claim format nor its issuer. RFC 9068 is one optional format profile; JWT itself does not turn a token into owner-originated authority. Conversely, opaque tokens plus introspection can satisfy the same header. The choice between local signature verification and online validation changes availability, revocation latency, privacy, and RS coupling; it is not determined by the header. Read RFC 6750 with the current OAuth security BCP, RFC 9700, which updates the security guidance in RFCs 6749 and 6750. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html), [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html), [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html), [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

### OAuth/OIDC and RFC 7523 are not the wallet proof standard

OIDC defines an interoperable identity layer based on authentication at an AS. An ID Token is for the client/RP to validate; API access is via an access token and separate RS semantics. RFC 7523 requires a signed JWT assertion with issuer, subject, AS audience, and expiry; its `jti` replay check is optional. It expressly relies on a pre-existing trust relationship and can be used without user approval at the AS. Therefore it is not a replacement for a wallet challenge/consent ceremony. The current proof is not formatted as the required JWT, and 7523's issuer/audience model would require deciding how the wallet/Identity key becomes a trusted assertion issuer at Keycloak. Keycloak's native RFC 7523 support solves the grant mechanics only after those trust/format choices. [OIDC Core](https://openid.net/specs/openid-connect-core-1_0-final.html), [RFC 7523](https://www.rfc-editor.org/rfc/rfc7523.html), [Keycloak JWT Authorization Grant guide](https://www.keycloak.org/securing-apps/jwt-authorization-grant)

### Making OAuth rights object- and purpose-specific

OAuth `scope` is useful but an AS-defined string namespace, not universal semantics for an object's digest, action, and purpose. RFC 9396 Rich Authorization Requests adds structured `authorization_details` with a required `type` whose meaning is defined by the relevant API; AS must return the granted details. This can carry fine-grained request data without changing JWT or Bearer presentation, but the ecosystem must define and version the type, resource identifiers, action vocabulary, purpose semantics, consent display/receipt, and what the storage RS enforces. [RFC 9396](https://www.rfc-editor.org/rfc/rfc9396.html)

OAuth Token Exchange (RFC 8693) can represent subject/actor and request a target resource token, but is an AS token derivation protocol, not an owner-signed capability-chain standard. [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)

### GNAP offers format flexibility, not a preselected ecosystem implementation

GNAP explicitly separates AS, client instance, resource owner, and RS, supports negotiated grants/consent, and supports structured or opaque token implementations. RFC 9767 supplies additional RS-facing validation, introspection, and token model guidance. Their proposed-standard status is mature IETF publication, but they are not OAuth wire compatible and the Keycloak documentation reviewed does not claim GNAP support. Selecting it implies evaluating a separate implementation and real client/wallet/RS interoperability—not simply changing a Keycloak token mapper. [RFC 9635 §§1, 3, 8](https://www.rfc-editor.org/rfc/rfc9635.html), [RFC 9767 §§1–3](https://www.rfc-editor.org/rfc/rfc9767.html)

### UMA/RPT fits centralized resource policy but not every trust boundary

Keycloak Authorization Services models resource, scope, permission, and policy; its UMA 2.0 flow issues permission tickets and RPTs, and docs describe user-managed resource permissions. That maps naturally to Storage Object + operation scopes, and RPT is a Bearer JWT. The model is still Keycloak-centric: the RS must register/represent resources and apply Keycloak policy; wallet-granted, purpose-bound consent UX and decentralized portability are not supplied automatically. Whether owners rather than provider/site admins actually manage storage permissions depends on deployment and user-facing controls. UMA's fine-grained authorization does not authorize provider capacity; operator quota checks stay local to storage. [Keycloak Authorization Services 26.8.0](https://www.keycloak.org/docs/26.8.0/authorization_services/), [Storage boundary](../../components/decent-simple-storage.md)

Keycloak exposes a custom Authenticator SPI, OIDC protocol mappers, and authorization services. That allows a custom Identity/Ed25519 verifier or token enrichment, but custom code is not native interoperability and must preserve nonce, exact-match, replay, consent, and fail-closed behavior. As of research date, Keycloak's own latest docs are 26.8.0; JWT Authorization Grant became supported in 26.6; DPoP is documented as supported. The implementation lead named by #36, `decent-keycloak`, returned GitHub 404 at the expected public URL during this research, so its code, maintenance status, and actual delta could not be independently assessed. Compare it with a maintainable external provider/SPI and a separate verifier/AS split before choosing. [Keycloak Server Developer Guide](https://www.keycloak.org/docs/latest/server_development/index.html), [JWT Authorization Grant](https://www.keycloak.org/securing-apps/jwt-authorization-grant), [Keycloak release notes](https://www.keycloak.org/docs/latest/release_notes/), [#36](https://github.com/jetpen/decent-ecosystem/issues/36)

## UCAN is capability-native; current HTTP profile is a versioning gap

UCAN v1 gives a resource-centered, DID-key-signed delegation chain, resource URI, subject and ability, attenuation, and separate invocation/revocation concepts. This is materially different from JWT access tokens issued by an AS: delegation provenance can be verified at the resource, but the resource/validator has to understand UCAN and the DID-method/key and revocation behavior. UCAN explicitly does not guarantee confinement/visibility of all downstream delegations when parties are offline. The community's linked delegation, invocation, and revocation documents still show `v1.0.0-rc.1` in their current README/repo status; the core v1.0.0 does not mean every sub-spec has a final 1.0 release. The revocation model is a monotonically growing revocation set/cache maintained by resource controller, not automatic global or immediate revocation. [UCAN v1 core](https://github.com/ucan-wg/spec), [Delegation v1.0.0-rc.1](https://github.com/ucan-wg/delegation), [Invocation v1.0.0-rc.1](https://github.com/ucan-wg/invocation), [Revocation v1.0.0-rc.1](https://github.com/ucan-wg/revocation)

The current published Bearer-header profile is not a v1 profile: its README is “UCAN as Bearer Token Specification v0.3.0,” last updated 2023; it encodes the entry UCAN as JWT and describes a second `ucans` header for proofs. The WG's current repository index marks this HTTP profile outdated relative to v1. The v1 core requires canonical DAG-CBOR encoding for signing (other presentation formats are transport-profile work); precise interoperable v1 HTTP encoding, compatibility of extra proof headers through proxies, and support in server libraries remain unresolved. It also states the recipient is `aud` and must sign, so it is not semantically an RFC 6750 bearer despite using that scheme name/header. This is conceptually aligned to owner-originated capabilities, but not plug-compatible with Keycloak OAuth/RPT and would require a new implementation/interop profile. [UCAN HTTP profile](https://github.com/ucan-wg/ucan-http-bearer-token), [WG index/status](https://github.com/ucan-wg), [UCAN v1 spec](https://github.com/ucan-wg/spec), [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html)

### DPoP is orthogonal and changes the auth scheme

DPoP reduces replay/theft risk by binding OAuth token to a client's key and signing request-specific proofs. It does not identify the wallet holder, add scopes, or replace a proof-of-control challenge. RFC 9449 uses the `DPoP` authorization scheme for bound access tokens rather than `Bearer`; accepting DPoP therefore requires a client and RS contract other than a literal Bearer-only target. Keycloak support is available, but RS integration, support in the chosen libraries, DPoP nonce/replay handling, and whether the wallet or application client owns this second key need decision. [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html), [Keycloak Server Administration Guide](https://www.keycloak.org/docs/latest/server_admin/index.html)

### DID Core is complementary, not interchangeable with current Identity

DID Core standardizes document structure, resolution concepts, and verification relationships, not DID methods, a wallet proof protocol, consent workflow, or access-token format. `authentication` is for authenticating the DID subject; capability delegation and invocation relationships are different purposes. DID Core's flexibility means method selection determines key discovery/update semantics and trust roots. The existing system instead uses an exact-match human-readable identifier and Registry-validated Identity Record, with no DID methods/DID Documents in the MVP. A future mapping could be studied, but claiming today's Identity lookup is DID resolution would be inaccurate. [W3C DID Core 1.0 §§5.3–5.4](https://www.w3.org/TR/2022/REC-did-core-20220719/), [Identity component boundary](../../components/decent-identity.md)

## Unresolved human choices and specification questions

This research intentionally does not recommend a scheme. The parent wayfinder still needs human decisions on:

1. Whether a centralized AS such as Keycloak is the root of trust for reusable resource credentials, while wallet proof remains the bootstrap; or whether resource-side validation of owner-signed capabilities is required.
2. What exact storage grant means: token subject (owner), client/actor, RS audience, object identity (digest or stable object URI), action set, purpose, expiry, and whether create/list/discover are distinct rights. Decide whether an RFC 9396 type, UMA resource/scope model, or capability vocabulary owns those meanings.
3. Who gives consent for each storage capability, how a wallet shows purpose/object/action, and how to prove the grant was bounded by that approval. Keep login, disclosure, resource consent, and provider enrollment/quota separate.
4. Whether RS validation must work offline; acceptable key/permission cache staleness; whether immediate revocation is required; outage and Registry/AS availability behavior; credential lifetime and refresh/re-authorization rules.
5. Whether the wire contract is strict `Bearer` only or may also support DPoP's `DPoP` scheme. If Bearer, decide acceptable credential formats; this header does not settle opaque vs JWT vs UCAN.
6. How the current Identity Record and exact-match key become an issuer/trust relationship at an AS (if selected), and what happens on key change, stale cache, alias collision, recovery, and key revocation.
7. Whether to choose the current Keycloak fork, an independently maintained Authenticator/extension, a separate wallet verifier plus standard AS, native UMA policy, GNAP, or resource-side UCAN. For Keycloak/fork evaluation inspect source, supported releases, tests/maintenance, migration and upgrade burden; no public `decent-keycloak` repository content was available at the research URL.
8. For UCAN specifically: confirm a maintained v1 HTTP profile, serialization/headers across proxies, Ed25519 suite and DID/key method compatibility, revocation retrieval and cache behavior, and interoperability with storage implementations before selecting it.
9. Decide WordPress session ownership and how access tokens relate to login. A site cookie/session may be preferable for browser login even if storage HTTP APIs consume a separate Bearer capability; avoid turning the wallet proof into either.

The newer DID Core 1.1 is a Candidate Recommendation Snapshot (5 March 2026), and DID Resolution v1 is a Candidate Recommendation Draft (1 October 2026), not final Recommendations. References above use 1.0 as the stable normative base; adopting 1.1/Resolution must account for draft maturity.
